3数据库字段设计（字段级）

通用约定：主键 BIGSERIAL；所有表默认含 created_at / updated_at TIMESTAMPTZ NOT NULL DEFAULT now()（通用约定列，下文仅在有特殊语义时列出）；需要并发编辑的档案带乐观锁列 version INT NOT NULL DEFAULT 1（更新时 version+1，不匹配报 1304）；删除一律用 status=0 停用，不物理删除。精度：金额 NUMERIC(14,2) / 单价 NUMERIC(14,4) / 数量 NUMERIC(14,3)，禁 float/double。表名 / 字段名 snake_case。以下字段定义与 v1.5 第 4 节 DDL 一一同构（Prisma schema 同构生成）。

5.3 后端全局异常过滤器（C4，处理顺序）

  1. BizError（业务层主动抛出，携带 code + message + 可选 details）→ 直接映射
  2. BadRequestException（ValidationPipe）→ 1001（details 取 constraints）
  3. HttpException 框架异常 → 按 status 反查 404/401/403
  4. Prisma 已知错误：P2002（唯一冲突）→ 1305；P2025（记录不存在）→ 1204
  5. 其余未知异常 → 1500：logger.error({ err, traceId }) 落错误日志（含堆栈），响应体不含堆栈
// BizError 用法（service 层）
throw new BizError(1301, `库存不足：${warehouse.name} - ${material.name}`);
throw new BizError(1307, '王五 2026-10 期间已全部结算，不可重复生成');
// 过滤器骨架
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exc: unknown, host: ExecutionContext) {
    const { code, message, details } = this.normalize(exc);   // 按上述顺序归一化
    const traceId = req.traceId;                              // 中间件已注入
    if (code >= 1500) logger.error({ err: exc, traceId, ...ctx });
    res.status(httpOf(code)).json({ code, message, details, traceId });
  }
}

6.4 traceId 贯穿规范

环节规则
生成请求中间件 first-touch：优先取请求头 X-Trace-Id（前端 axios 拦截器生成 t-+12 hex），无则服务端 crypto.randomBytes(6) 生成；每请求唯一
注入Nest 中间件写入 AsyncLocalStorage；pino 子 logger 自动携带；service / repository 无需手工传参
返回响应头 X-Trace-Id 回显；错误响应体 traceId 字段；成功响应体也带（便于对账）
前端axios 每请求生成（重试复用同一个）；响应拦截器 console.debug 打印 traceId（截图报障用）；错误弹窗展示可复制
跨日志关联同一 traceId 可在 app/error 两个文件 + Nginx access（$request_id 附注）中检索；运维命令：grep 't-8f3a' logs/*.log
定时任务cron 每次运行生成独立 traceId（前缀 t-cron-），预警产生异常可追溯当次扫描

9.1 幂等与防重复提交

9.2 并发控制

  • 事务边界：所有多表写操作在 service 层单事务（withTransaction，C1 组件）；任一步失败整体回滚——"半审核""半结算"状态不可能存在
  • 库存扣减：SQL 条件更新 UPDATE stock SET qty = qty - :n WHERE ... AND qty >= :n，行数=0 即返回 1203（库存不足），杜绝并发负库存
  • 均价更新：同物料并发入库用 pg_advisory_xact_lock(material_id) 串行化重算（v1.5 §8 精度规范）
  • 乐观锁：档案编辑带 version（PUT 校验不符返回 1304）；单据状态流转用状态机条件更新（如 WHERE status='confirmed'），冲突返回 1309/1204
  • 死锁：Prisma 超时 5s + 死锁自动重试 2 次（间隔退避），仍失败返回 1501 并记 error 日志

9.4 安全清单

  • 密码：初始 6 位数字；自设 ≥8 位不限复杂度；bcrypt(cost≥10)；重置 → token_version+1 全端失效；首登强制改密（1103 拦截）
  • 登录防护：失败 5 次锁 15 分钟（1102）；/auth/login 限流 5 次/分/IP（1104）；登录日志含 IP（§6.5）
  • 越权：所有 /me/* 接口后端强制 employee_id = 当前用户绑定员工；计件产品白名单防止跨员工价格泄露（§7.6）
  • 注入与 XSS：Prisma 参数化 + 查询字段白名单（1003）；前端不渲染富文本 HTML；上传文件类型/大小校验（jpg/png/webp ≤3MB）+ 路径穿越防护 + 重命名为 UUID
  • 密钥管理：只在后端 .env（git 忽略 + example 模板）；前端零密钥；JWT secret ≥32 位随机
  • 传输：全站 HTTPS（Nginx 终止）；refreshToken httpOnly + Secure + SameSite=Strict（Web）/ SecureStorage（APP）
  • 审计：红冲/改价/重置密码/库存调整/审核/结算确认全覆盖（§6.5），与业务同事务

9.5 备份与恢复

  • pg_dump 每日 01:30 全量（cron），保留 7 天滚动 + 每月 1 日一份留 30 天；备份完成/失败写日志并通知 sys_admin
  • 每季度恢复演练到临时库：验证备份可用性 + 关键表行数抽样比对，演练结果记审计
  • 文件（报工照片）：每日 rsync 至备份盘，与数据库备份同保留策略
  • RPO ≤24h（MVP 可接受，单企业部署）；恢复步骤文档化：停服务 → 恢复库 → 重放当日备份后二进制日志（如启用）→ 校验
